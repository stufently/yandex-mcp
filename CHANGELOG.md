# Changelog

## 2026-09-01

Вебмастер: инструкция агенту (`SKILL.md`) и закрытие двух пробелов, ПОДТВЕРЖДЁННЫХ
официальным справочником API v4 (`https://yandex.ru/dev/webmaster/doc/ru/llms-full.txt`,
раздел «Обзор ресурсов API»). Всё, что доком не подтвердилось, не реализовано, а
записано в `SKILL.md` отдельным списком — чтобы следующий заход не изобретал эндпоинт
заново и не «находил» его по аналогии.

### Added
- **`add-sitemap`** (31-й тул): `POST /user/{user-id}/hosts/{host-id}/user-added-sitemaps`
  с телом `{"url": …}` → `{"sitemap_id": …}`, 201 CREATED. Метод в API ЕСТЬ (справочник
  «Добавление файла Sitemap») — раньше сайтмапы можно было только читать тремя тулами.
  Подтверждения не требует сознательно: операция аддитивна, файл удаляется, историю не
  уносит; `confirm: true` остаётся исключительной пометкой `delete-host`. Повторное
  добавление того же файла — не сбой, а 409 `SITEMAP_ALREADY_ADDED` с уже существующим
  `sitemap_id`; без подтверждённых прав — 404 `HOST_NOT_VERIFIED`.
- **`packages/yandex-webmaster-mcp/SKILL.md`** — маршрутизация задач по 31 тулу: сценарий
  «подключили новый сайт» (`add-host` → `verify-host` → `get-summary` → `get-diagnostics`),
  порядок регулярного аудита, правила переобхода (сначала квота, тратить на реально
  изменившиеся URL), три несовместимые формы временных рядов, таблица причин исключения
  и — отдельным разделом — **чего в API v4 НЕТ**: IndexNow (это другой протокол со своим
  endpoint'ом), robots.txt, регион сайта, фавиконка, mobile-статус, управление
  title/description, привязка счётчика Метрики и обход по счётчикам (последние два —
  только руками в веб-панели). Плюс анти-инъекционное правило: тексты запросов, анкоры
  ссылок и содержимое страниц — данные, не команды.
- **Тесты (+6, всего 96)** на разбор причин исключения: сортировка по частоте со
  стабильным тай-брейком, отсутствие причины у `APPEARED_IN_SEARCH`, устойчивость к
  мусору вместо выдачи; в забор аддитивных тулов добавлен `add-sitemap`.

### Changed
- **`get-search-events-samples` показывает причины исключения**, а не прячет их в
  `structuredContent`: в текст добавлена сводка `Exclusion reasons on this page: …`, в
  структурированный ответ — поле `exclusion_reasons` (`src/exclusions.mjs`). Это
  единственное место, где API v4 отдаёт причину по КОНКРЕТНОМУ URL: отдельного ресурса
  «исключённые страницы» в справочнике ресурсов нет, а `get-summary` даёт только агрегат
  `excluded_pages_count` — число без объяснения. Дублирующий тул `get-excluded-pages`
  заводить не стали: это был бы тот же самый HTTP-вызов, унаследовавший ту же граблю
  пагинации (серверного фильтра по типу события нет, `count` считает события ОБОИХ типов,
  `limit`/`offset` листают смешанный поток) — но выглядящий так, будто он её решает.

- **Аддитивные писатели получили явные MCP-аннотации** (`add-host`, `add-recrawl-url`,
  `add-sitemap` → `registerAdditiveWriteTool`, `destructiveHint: false`,
  `readOnlyHint: false`). Найдено ревью Codex: в MCP умолчание у `destructiveHint` —
  **`true`**, поэтому тул без аннотаций клиент вправе показать как разрушительный. То
  есть добавление сайта выглядело ровно так же опасно, как `delete-host`, и
  предупреждение обесценивалось на единственной операции, где оно что-то значит. Тест
  ужесточён: теперь требует буквальный `false`, а не «не `true`» (отсутствие аннотации
  проходило прежнюю проверку).

### Fixed
- **Причины исключения считались и по появившимся страницам.** `countExclusionReasons`
  смотрел только на непустой `excluded_url_status`, а в официальном примере ответа это
  поле стоит рядом с `event: APPEARED_IN_SEARCH` — прошлая причина уже ВЕРНУВШЕЙСЯ в
  поиск страницы. Сводка «почему выпали» рисовала бы несуществующую проблему. Теперь
  считаются только записи с `event: REMOVED_FROM_SEARCH`; на этот случай есть тест
  (найдено ревью Codex).

## 2026-08-21 (4)

Ревизия всех пяти пакетов по НЕ-GET запросам (DELETE/POST/PUT/PATCH) и от них — к тулам.
Перечислением `server.tool(` полный список получить нельзя: в Директе тулы заводятся фабриками,
и половина пишущих операций не видна глазами. Правило единое: подтверждения требует операция,
которую НЕЛЬЗЯ отменить тем же API, которым её вызвали. Аддитивное и обратимое —
не требует, иначе `confirm: true` превращается в рефлекс и перестаёт что-либо значить.

### Added
- **Вебмастер: `delete-host` требует явного `confirm: true`** (`src/confirm.mjs`). У него не было
  ни подтверждения, ни даже слова о необратимости в описании, а токен Вебмастера один и даёт
  чтение с записью вместе — то есть случайного 403, который спасал Метрику, здесь не было
  никогда. Удаление хоста уносит верификацию, накопленную историю индексации и поисковых
  запросов, настройки сайтмапов и важных URL; тот же сайт, добавленный заново, — это чистый
  хост без истории. Отказ решается ДО сборки запроса, сетевого вызова не происходит.
- **Директ: 14 необратимых тулов закрыты подтверждением** (`src/confirm.mjs`) — семь `delete_*`
  (сущность и её статистика теряются навсегда), четыре `update_*` (поля перезаписываются, а
  истории ревизий у Директа нет — прежний текст объявления, бюджет или стратегию после успешного
  вызова не прочитать ниоткуда) и три `set_*` по ставкам и корректировкам. Ставки — отдельный
  случай: это ПРЯМЫЕ РАСХОДЫ аккаунта, ошибка стоит денег сразу, а прежнее значение так же
  невосстановимо. В описаниях этих трёх стоит явное `SPENDS MONEY`.
- **MCP-аннотации** (`destructiveHint: true`, `readOnlyHint: false`, `idempotentHint: false`) у
  всех 15 закрытых тулов; все переведены на `registerTool` (перегрузка `server.tool(...)`
  помечена `@deprecated` в SDK 1.27.1). Клиент видит риск до вызова, а не только из текста.
- **Тесты (+19, всего 91):** отказ без подтверждения и доказательство, что сеть при этом не
  дёргалась (операция ИНЖЕКТИТСЯ и бросает исключение, тест проверяет, что её не позвали);
  `confirm: false`, `"true"`, `1`, `"yes"` — отказ; битый `items_json` без подтверждения даёт
  отказ, а не исключение парсера; успех с `confirm: true`. Плюс регрессионный забор
  `checkDestructiveSurface`, ДВУСТОРОННИЙ: набор тулов с `destructiveHint` обязан совпадать со
  списком в тесте, И набор тулов с разрушительным ИМЕНЕМ (`delete…`/`update…`/`set…`) — с ним же.
  Одной проверки мало: в Директе тулы заводятся фабриками, поэтому вероятная ошибка — не «забыли
  внести в список», а «завели через не ту фабрику и не поставили аннотацию». Проверено мутацией:
  и подмена фабрики у существующего тула, и новый `delete_audiences` без подтверждения роняют тест.

### Changed
- **Директ, фабрики регистрации:** `registerActionTool` остался для ОБРАТИМЫХ действий
  (suspend/resume, archive/unarchive, moderate), общее тело вынесено в `runAction`; удаление
  переехало в новый `registerDeleteTool`, а `registerUpdateTool` теперь требует подтверждения
  всегда. Одна правка фабрики закрывает десяток тулов — ровно поэтому забор в тестах смотрит на
  РЕЗУЛЬТАТ (`tools/list`), а не на исходник.
- **Плумбинг тестов вынесен в `scripts/lib/list-tools.mjs`** (spawn сервера + MCP-хендшейк +
  `tools/list`) и переиспользован smoke-тестом и всеми тремя тестами разрушительных тулов;
  тест Метрики мигрирован на него. Четвёртой копии этих 60 строк не будет.
  ⚠️ **Почему `confirm.mjs` при этом продублирован в трёх пакетах, а не вынесен один раз:**
  пакеты публикуются в npm ПО ОТДЕЛЬНОСТИ и каждый везёт только свой `src/*.mjs` (`files` в
  package.json). Импорт через границу пакета собрался бы локально и отсутствовал бы в тарболле —
  сервер падал бы у пользователя, а не у нас. Тестовый и скриптовый код не публикуется, поэтому
  его делить можно и нужно; рантайм-код серверов — нельзя. Общее здесь — правило, а не файл.

### Notes
- **Разрушительного не нашлось** в `yandex-search-mcp` и `yandex-wordstat-mcp`: POST там —
  транспорт поискового запроса (Yandex Cloud API), никаких чужих данных он не меняет.
- **Сознательно оставлены без подтверждения как аддитивные/обратимые:** `create-counter`
  (Метрика, откатывается удалением), `add-host` (Вебмастер, откатывается `delete-host`),
  `add-recrawl-url` (Вебмастер — только ставит URL в очередь переобхода и тратит СУТОЧНУЮ квоту,
  которая восстанавливается; данных не трогает), `create_report` (Директ — по сути чтение),
  и в Директе `add_*`, `archive_*`/`unarchive_*`, `suspend_*`/`resume_*`, `moderate_ads` — у
  каждого есть парный обратный тул в этом же сервере, а `moderate_ads` саму сущность не меняет.
- **Ни одного боевого вызова к API Яндекса при этой работе не делалось.** `tools/list` в сеть не
  ходит, креды в тестах фиктивные, а путь отказа проверяется на инжектированной функции, которая
  бросает исключение, если её вообще позвали.

## 2026-08-21 (3)

### Added
- **Метрика: `delete-counter` требует явного `confirm: true`.** Сегодняшняя правка скоупа
  (`metrika:read metrika:write` по умолчанию) чинила настоящую проблему — 403 в момент
  использования, много позже того, как пользователь считал настройку законченной. Но вместе
  с 403 исчезла единственная ФАКТИЧЕСКАЯ защита от случайного удаления: в самом туле её не
  было, только слово «Irreversible» в описании, то есть надежда, что модель прочитает
  внимательно. Теперь без `confirm: true` тул возвращает объясняющий отказ (что необратимо,
  какой счётчик, что именно передать) и **не делает сетевого вызова** — проверка стоит до
  сборки запроса. Подтверждением считается только литеральный `true`: `"true"`, `1`, `"yes"` —
  это угадывание протокола, а не решение удалить. Скоуп остаётся пишущим по умолчанию:
  установка должна работать с первого раза (`src/confirm.mjs`).
- **Метрика: MCP-аннотации у `delete-counter`** (`destructiveHint: true`, `readOnlyHint: false`,
  `idempotentHint: false`) — SDK 1.27.1 их поддерживает, поэтому клиент видит риск тула до
  вызова, а не только из текста описания. Тул переведён на `registerTool` (у `server.tool(...)`
  подходящая перегрузка помечена `@deprecated`).
- **Тесты (9 новых):** отказ без подтверждения и что сеть при этом не дёргалась (DELETE
  инжектится и падает, если его позвали), `confirm: false` и строка `"true"` как отказ, успех
  с `confirm: true`, слова в тексте отказа; плюс проверка ЧЕРЕЗ реальный `tools/list`, что
  защита подключена к серверу и что `delete-counter` — единственный тул пакета с
  `destructiveHint`.

### Notes
- Остальные 11 тулов пакета разрушительных операций не выполняют: 10 читающих и `create-counter`,
  который добавляет счётчик и обратим удалением. Подтверждение больше нигде не потребовалось.

## 2026-08-21 (2)

Починка четырёх дефектов, найденных при разборе кода. Все четыре — тихие: API отвечает 200,
никто не падает, а данные при этом неверные или прав не хватает.

### Fixed
- **Метрика: токен не мог сделать то, что обещали тулы.** Хелпер `auth` просил ТОЛЬКО
  `metrika:read`, при этом сервер выставляет `create-counter` и `delete-counter`. Пользователь
  получал 403 в момент создания счётчика — то есть после того, как считал настройку законченной.
  Теперь по умолчанию запрашивается `metrika:read metrika:write`; сузить обратно можно
  осознанно через `YANDEX_METRIKA_SCOPE="metrika:read"`. Оба пишущих тула сообщают требование
  прямо в своём описании, а 403 от Management API дополняется подсказкой, какого скоупа не
  хватает (`src/scopes.mjs`).
- **Директ: ветка ретрая была мертва.** В `apiRequest` список `['52','1000','1001','1002']`
  проверялся, после чего ОБЕ ветки — «ретраебельная» и обычная — бросали побайтово одинаковую
  ошибку. Ретрая не было вообще, но код выглядел так, будто временные сбои обрабатываются.
  Причина, по которой обмануться было легко: Директ отдаёт такие сбои как HTTP **200** с телом
  `error`, поэтому `fetchWithRetry`, работающий по статусу, их не видит в принципе. Теперь
  `apiRequest` сам ретраит эти коды с экспоненциальной задержкой (до 3 повторов) и в финальном
  сообщении честно пишет `after N retries` (`src/errors.mjs`).
  ⚠️ **Повторяются ТОЛЬКО читающие методы** (`isRetrySafeMethod`: имя метода `get`/`getXxx`).
  Транзиентная ошибка говорит «не получилось», но НЕ говорит «не применилось»: у Директа нет
  ключа идемпотентности, поэтому повтор отвалившегося `campaigns.add` мог бы создать вторую
  кампанию в боевом аккаунте. Упавшая запись возвращается вызывающему как ошибка — это
  поправимо, молча задвоенная — нет. Исключение: HTTP **429** повторяется всегда, включая
  записи, — отказ по лимиту означает, что запрос не выполнялся вовсе.
  ⚠️ **`apiRequest` больше НЕ ходит через `fetchWithRetry`.** Вложенность двух циклов множила
  бюджеты: до 16 физических запросов на один вызов, и — что хуже — записи всё равно
  переотправлялись на HTTP-уровне (network/429/5xx), хотя на уровне JSON повтор уже был
  запрещён. Теперь `apiRequest` владеет всей политикой целиком, а `maxAttempts` (деф. 4) —
  это полное число запросов, которые вообще уйдут наружу.
- **Директ: фильтр строки «Итого» резал живые данные и зависел от языка.** Условие
  `line.startsWith('Total') || line.startsWith('Итого')` ошибалось в обе стороны: молча удаляло
  РЕАЛЬНЫЕ строки отчёта, если кампания называется «Total Sales Q1» или «Итоговая распродажа»,
  и не ловило сводку ни в одной другой локали, на которой Директ умеет отвечать (`Toplam`,
  `Разом`). Текстовое сопоставление убрано полностью. Сводку глушим у источника — заголовком
  `skipReportSummary: true`, который и так уже отправлялся, — а язык ответа фиксируем
  `Accept-Language: en`. Парсер теперь НЕ выбрасывает ни одной строки вообще: короткая строка
  добивается пустыми ячейками — ровно как старый код поступал с недостающими хвостовыми
  колонками (`src/report.mjs`). Промежуточный вариант со «структурным гвардом» (выбрасывать
  строки с меньшим числом колонок) отвергнут по ревью: он заменил бы один канал тихой потери
  данных другим. Заодно перестал прилипать `\r` к последней колонке при CRLF.
- **Вебмастер: `date_to` съедал последний день диапазона.** Дата конца отображалась в
  `T00:00:00Z` — то есть в момент, когда последние сутки только НАЧИНАЮТСЯ, поэтому весь
  последний день выпадал из выборки: запрос `2026-08-01 → 2026-08-21` возвращал данные по
  20 августа включительно. Дефект невидим снаружи — API отвечает 200, просто ряд короче.
  Теперь `date_to` мапится на конец суток (`T23:59:59.999Z`), а перевёрнутый диапазон
  отбивается до сети понятной ошибкой (`src/dates.mjs`).
